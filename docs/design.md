# Устройство

Почему раннер устроен так. Подробности в коде — docstring модулей `process`, `session`,
`transport`; здесь — решения целиком.

## Модули

| Модуль | Что делает |
| --- | --- |
| `process.py` | процесс Maya: скрытый рабочий стол, job object, приоритет, процессоры |
| `session.py` | каталог сеанса, окружение Maya, `userSetup.py`, `state.json`, уборка |
| `transport.py` | всё про dcc-mcp: ожидание сервера, рукопожатие, маркер, вызов кода, `maya-busy` |
| `config.py` | `[tool.maya_harness]` из `pyproject.toml` проекта |
| `cli.py` | команды `start`, `stop`, `status`, `exec`, `doctor` |

## Процесс Maya

* **Скрытый рабочий стол.** Заставка Maya забирает фокус даже у свёрнутого процесса, а окна,
  которые открывает выполняемый код, закрыли бы работу пользователя.
* **Job object.** Maya и всё, что она запустила, живут в job object, который убивает их при
  закрытии своего дескриптора: при ошибке, по Ctrl+C и когда убит сам раннер. Не `quit`:
  убийство не встаёт на модальном диалоге, а настройки этой Maya всё равно выбрасываются.
  Maya создаётся приостановленной и попадает в job до первой инструкции.
* **`start` отпускает Maya.** После старта job снимает свои ограничения и закрывается: Maya
  живёт дальше без раннера, и закрывает её отложенный `quit` из `stop` или таймер простоя. Maya,
  не принявшую `quit` (модальный диалог), `stop` убивает — только если pid по-прежнему её: образ
  `maya.exe` и время создания из `state.json`.
* **Приоритет и процессоры.** Ниже обычного приоритета и, если логических процессоров больше
  8, без первых 4: компьютер остаётся отзывчивым.

## Сеанс

* **Свой `MAYA_APP_DIR`.** `FBXPushSettings` пишет туда файл, и две Maya с одним каталогом
  ломают друг другу импорт FBX («Read settings failed»).
* **Своё окружение.** Из окружения пользователя убрано всё, что говорит Maya и Python, где
  искать код: `MAYA_*`, `PYTHONPATH`, `PYTHONHOME`, `PYTHONSTARTUP`, `VIRTUAL_ENV`. Иначе в Maya
  сеанса попали бы модули и плагины Maya пользователя. `PATH` остаётся как есть.
* **Свой `APPDATA`.** Плагины хранят там настройки (studiolibrary — `%APPDATA%\StudioLibrary`):
  сеанс не должен ни читать, ни переписывать настройки пользователя. `LOCALAPPDATA` остаётся:
  там вход в Autodesk.
* **Маркер.** Maya сеанса отличает `MAYA_HARNESS_WORK` — её рабочий каталог. Раннер выполняет
  код только в Maya с маркером: у Maya художника его нет, а сценарий может открыть новую сцену
  и выбросить его работу.
* **`state.json`, а не имя каталога.** Каталог `maya_harness_<project>_<pid>_*` держит живой
  раннер или живая Maya из `state.json`. Pid из имени не разобрать: после префикса стоит имя
  проекта, а в нём бывает `_` (`Retarget_Master`). Живость Maya — pid вместе с временем создания
  из `state.json`, как у `stop`: Windows отдаёт pid закрытой Maya другому процессу.
* **Контрольная сумма `userSetup.py` выключена.** `userSetup.py` в каждом сеансе новый, и без
  этого `quit` встаёт на модальном окне «Secure UserSetup Checksum verification». Заранее
  записанный `userPrefs.mel` не помогает: первый старт Maya в новом каталоге настроек его
  игнорирует.
* **Таймер простоя.** Забытая Maya на скрытом рабочем столе руками не закрывается: `userSetup.py`
  раз в минуту сравнивает возраст `work/last_call` с `--ttl` и закрывает Maya. `exec` обновляет
  `last_call` и до, и после вызова: таймер в главном потоке молчит, пока идёт вызов, и без
  обновления после долгого вызова Maya закрылась бы сразу.

## Транспорт

* **dcc-mcp in-process** на свободном порту, который раннер выбирает сам (`DCC_MCP_MAYA_PORT`).
  `DCC_MCP_MAYA_SIDECAR=0` и `DCC_MCP_GATEWAY_PORT=0` держат эту Maya вне gateway пользователя.
* **Весь dcc-mcp — в `transport.py`.** Остальной пакет зовёт `execute(url, code, timeout)`.
  Свой сервер в `userSetup.py` вместо dcc-mcp отложен: не проверено, вкладывается ли вызов в
  открытие сцены; заменить можно одним модулем.
* **`maya-busy`.** Патч DCC_MCP отказывает вызову, пришедшему, пока Maya открывает или
  сохраняет сцену: вложенный в `file -open`, он увидел бы сцену загруженной наполовину. `exec`
  повторяет такой вызов до своего таймаута. Отказ распознаётся по полю `error` ответа, а не по
  тексту: stdout выполненного кода тоже может содержать `maya-busy`, и повтор выполнил бы код
  второй раз.
* **Таймаут у каждого вызова.** Вызывающий может делить один общий срок между вызовами.
* **Ответ читается в потоке.** На Windows блокирующее чтение сокета держит Ctrl+C до ответа;
  ожидание потока его пропускает.
