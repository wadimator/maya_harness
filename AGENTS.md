# AGENTS.md

## Описание проекта

maya_harness — пакет и команда `maya-harness`: изолированная GUI-Maya 2025 для разработки
плагина. Поднять Maya на скрытом рабочем столе, выполнить в ней код через
[dcc-mcp-maya](https://github.com/dcc-mcp/dcc-mcp-maya), посмотреть состояние, закрыть.
Плагины подключают пакет dev-зависимостью; детали — [README.md](README.md).

Главные приоритеты:

* простота;
* понятный и поддерживаемый код;
* исправление первопричин, а не симптомов.

## Команды

* Всё сразу: `just check` — `uv lock --check`, формат, линтер, mypy, тесты
* Тесты: `just test`; линтер: `just lint`; формат: `just fmt` (проверка — `just fmt-check`);
  типы: `just types` (strict)
* Окружение: `just sync` — `uv sync --frozen --exact`; хуки: `just install-hooks` — один раз в
  свежем клоне
* Выпуск версии: `just release-prep X.Y.Z` — коммит версии, тег, колесо, черновик описания;
  push и релиз — руками ([docs/contributing.md](docs/contributing.md), «Версия и релиз»)
* Запуск: `uv run --frozen --exact maya-harness <команда>` — `start`, `stop`, `status`,
  `exec`, `doctor`; **требует Maya 2025 и dcc-mcp-maya**

## Инварианты проекта

* Только стандартная библиотека Python: `dependencies = []`.
* Только Windows и Maya 2025: скрытый рабочий стол и job object — Win32 API через `ctypes`.
* Пакет ничего не знает о конкретных плагинах и о репозиториях, которые его используют: пути,
  плагины Maya и имя проекта приходят настройками (`[tool.maya_harness]` или параметрами
  сеанса).
* Весь dcc-mcp — в `transport.py`: остальной пакет зовёт `execute(code, timeout)`.
* Код выполняется только в Maya, которую поднял maya_harness: её отличает маркер в окружении,
  и `connect` отказывает Maya без него.
* Документы — на русском, без личных путей и имён машин; docstring и комментарии — на
  английском.
* Как это выглядит в коде — [docs/codestyle.md](docs/codestyle.md).

## Рабочий процесс

План задачи — `tasks/<тип>/<кратко>.md`, имя совпадает с веткой. Если задача ведётся в
рабочем пространстве над несколькими репозиториями и план уже лежит там, локальный файл не
создаётся. Каталог `tasks/` — в `.gitignore`, ссылки на него в код и `docs/` не попадают.

Перед реализацией создай или обнови план: цель, короткий план с чекбоксами, затрагиваемые
области, критерии готовности. После завершения — краткий обзор: что изменено, какие проверки
выполнены, что осталось.

Проверенный вывод, на котором легко ошибиться снова, — сразу в `docs/` или в docstring кода.
Про конкретное место кода — docstring или комментарий «почему» у этого кода, про область — её
документ в `docs/`. Неясно, стоит ли записывать, или подходящего документа нет — спроси
пользователя, а не решай молча. Очевидное и одноразовое не записывай.

«Изучи», «дай рекомендации», «проверь» — анализ без правок отслеживаемых файлов до явной
просьбы реализовать.

Файлы — UTF-8 без BOM, LF (`.gitattributes`). Правка — инструментами Edit и Write: запись из
PowerShell (`Set-Content`, `Out-File`) портит кодировку.

Один пункт плана — один коммит сразу после проверки, только его файлы. Git-процесс — в
[docs/contributing.md](docs/contributing.md).

## Основные правила

* **Делай проще.** Без абстракций, зависимостей и файлов, без которых задача решается.
* **Исправляй причину.** Не маскируй проблему обходами, не отключай проверки.
* **Меняй только нужное.** Найденное попутно — отдельным пунктом плана.
* **Проверяй результат.** `just check`; новый тест принимается мутацией: сломай код и убедись,
  что тест упал. Запуск Maya — вручную по [README.md](README.md): в `check` его нет.

В финальном ответе кратко перечисли: что сделано, где сделано, чем проверено.
